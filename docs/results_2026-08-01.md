## 요약

요청한 연구용 토이 프로젝트를 이 컴퓨터에서 실제로 끝까지 실행해 보았다. 작은 Transformer의 from-scratch 학습, 로컬 Qwen의 CPT/full SFT/LoRA/QLoRA/양자화/증류/DPO, Qwen3-VL-8B 실제 이미지 추론, 여섯 가지 ML 실험, 로컬 Qwen Coder가 파일을 만들고 Podman 안에서 검증하는 agent loop까지 결과물이 생성되었다.

결과를 다음 네 종류로 구분한다.

- **실제 로컬 모델 실행**: `${FMLAB_MODEL_ROOT}`의 weight로 forward/backward/generation을 수행
- **실제 교육용 구현**: 작은 모델·합성 데이터지만 loss와 optimizer를 실제 계산
- **시뮬레이터**: 데이터·평가·보고 경로만 결정론적으로 검증; 모델 성능이 아님
- **준비 완료**: 코드·설정·데이터 형식은 구현했지만 장시간 학습은 의도적으로 미실행

기본 학습은 `max_steps=2` 또는 매우 작은 데이터로 제한했고 `save_model=false`를 사용했다. 따라서 아래 수치는 기능과 학습 방향을 검증하는 smoke 결과이며 최종 품질 비교가 아니다.

### 1.2 Transformer from scratch

구분: **실제 교육용 구현·학습**

68,016개 파라미터, 2 layer, 4 attention head, 폭 48, context 48인 decoder-only Transformer를 CPU에서 20 step 학습했다. causal attention, RoPE, RMSNorm, SwiGLU, tied embedding이 직접 구현되어 있다.

| 지표 | 학습 전 | 학습 후 |
|---|---:|---:|
| next-token loss | 5.5625 | 3.6543 |
| perplexity | 260.48 | 38.64 |

loss가 1.9082 감소해 optimizer와 causal label 경로가 정상적으로 동작했다. 생성문은 tiny corpus를 외우기 시작하는 수준이며 언어 품질을 평가하기 위한 모델은 아니다. layer 0/head 0의 attention 행렬을 SVG로 남겨 query token이 과거 key 중 어디에 가중치를 두는지 확인할 수 있다.

### 1.3 전체 toy objective suite

구분: **실제 교육용 구현**, 단 QLoRA/INT4 packed kernel은 **수치 simulation**

최종 통합 실행은 CUDA에서 objective당 3 step, seed 7로 실행했다.

| 실험 | 핵심 결과 | 해석 |
|---|---:|---|
| from scratch | loss 5.5405 → 5.0777 | next-token 학습 방향 확인 |
| continued pretraining | domain loss 5.6007 → 5.4528 | 새 문체 적응 경로 확인 |
| full SFT | final loss 5.1360 | prompt label mask를 둔 response 학습 |
| LoRA | final loss 5.2949, trainable 1.354% | base를 고정한 저랭크 경로 |
| simulated QLoRA | final loss 5.2933, trainable 1.518% | dequantized base 위 adapter gradient |
| INT8 simulation | 3.58×, cosine 0.999986 | 작은 왜곡과 압축 |
| INT4 simulation | 6.47×, cosine 0.995294 | 더 큰 압축과 더 큰 왜곡 |
| distillation | loss 1.6791 → 1.6340 | student가 teacher 분포 쪽으로 이동 |
| DPO | loss 0.6931 → 0.6335 | chosen margin이 증가하기 시작 |
| BM25 RAG | Recall@2 0.50, MRR 0.50 | 한국어 공백 tokenization 한계 노출 |

전체 실행은 약 0.97초였다. RAG 0.5는 숨겨야 할 실패가 아니다. `비트`와 `비트로` 같은 표면형을 다른 token으로 보는 단순 tokenizer 때문에 검색이 놓친 사례이며, character n-gram과 dense embedding 비교의 기준점이다.

### 2.3 VLM LoRA와 증류

구분: **구현·설정·데이터 준비 완료, 장시간 학습 미실행**

- Qwen3-VL-8B의 vision encoder를 동결하고 language projection에 rank 16 adapter를 붙이는 recipe
- rank/target module/vision freeze/visual token budget ablation 설정
- Qwen3-VL-30B-A3B-Thinking-FP8와 32B-Instruct-FP8 teacher profile
- canonical manifest 준비: 문서 4, 차트 4, grounding 16, mixed 24 rows

32B teacher 전체 학습이나 VLM 8B 장시간 LoRA는 smoke 범위를 넘어 실행하지 않았다. 구현 범위와 다음 평가 설계는 `docs/vlm_track.md`에 있다.

## 4. 코드 에이전트 결과

구분: **실제 모델-도구 loop + 실제 격리 실행**

에이전트는 파일 도구와 argv 기반 run만 사용하고 shell string은 실행하지 않는다. 모델이 완료를 선언하더라도 마지막 파일 변경 뒤 성공한 test/run이 없으면 validation gate가 거부한다.

### 보안 경계

실제 model-generated code는 `PodmanRunner` 안에서 실행했다.

- `--network=none`, `--pull=never`
- read-only root filesystem과 noexec 임시 공간
- 모든 capability 제거, `no-new-privileges`
- CPU/RAM/PID/시간/출력/파일 크기 제한
- disposable workspace 하나만 `/workspace`에 read/write mount
- `python -c`, traversal, 외부 absolute path, 비허용 executable 거부

호스트 bubblewrap는 namespace 생성 중 `RTM_NEWADDR` 제약으로 동작하지 않았다. 그래서 bwrap historical trace는 격리 성공 근거로 세지 않고 Podman 실행만 검증 근거로 사용했다.

### 실행 결과

| run | 상태 | 의미 |
|---|---|---|
| `podman-demo` | completed, 6 step | 잘못된 구현→실패→수정→통과의 deterministic loop |
| `qwen-coder-3b-real` | completed, 5 step | 로컬 3B가 파일과 run을 사용; test 함수가 호출되지 않은 semantic false positive 포함 |
| `qwen-coder-3b-pytest` | step_limit, 10 step | pytest가 `no tests ran`을 정확히 실패 처리; 모델이 malformed JSON을 복구하지 못함 |
| `qwen-coder-3b-verified` | completed, 4 step | 세 top-level assert와 `3 assertions passed`를 Podman에서 확인 |

기록된 7개 run 중 완료는 5개, 성공한 network-isolated run이 있는 완료는 4개였다. 가장 신뢰할 수 있는 실제 모델 결과는 `qwen-coder-3b-verified`다.

- `${FMLAB_DATA_ROOT}/agent-sandboxes/qwen-coder-3b-verified/report/trace.html`
- `${FMLAB_DATA_ROOT}/agent-sandboxes/qwen-coder-3b-pytest/report/trace.html`

이번 실행에서는 checkpoint를 저장하지 않았다. 기존 공유 모델 중 실제 사용한 weight 디렉터리 크기는 0.5B 약 954MiB, 3B instruct 약 5.8GiB, coder 3B 약 5.8GiB, VLM 8B 약 17GiB지만 이미 존재하던 공용 저장 공간이므로 프로젝트 증가량에 포함하지 않았다.

장기 실험 시 예상 증가량은 다음 요인에 의해 결정된다.

- LoRA adapter: 보통 수십~수백 MiB
- merged/full model: 원본 weight 크기와 비슷하거나 dtype에 따라 더 큼
- optimizer state: full fine-tuning에서는 모델 weight의 몇 배가 될 수 있음
- teacher response cache: response text는 작지만 logits 전체 저장은 매우 큼
- 이미지/비디오: frame 추출 수와 해상도에 선형 비례

`/home`이 98% 사용 중이므로 모든 checkpoint, dataset, cache는 계속 `/data`에 두어야 한다.

- long prompt SFT label-mask edge case
- CUDA model evaluation regression
- VLM synthetic/evaluation/inference/tiny model
- 여섯 ML experiment smoke
- agent workspace traversal, completion validation, Podman command construction과 보안 옵션

최종 상태에서 **60개 테스트가 모두 통과**했고 ruff lint/format 검사도 통과했다.

재검증 명령:

```bash
cd /path/to/foundation-model-lab
source scripts/env.sh
source ${FMLAB_DATA_ROOT}/envs/fmlab/bin/activate
pytest -q
```

알려진 한계:

1. smoke 데이터가 작아서 방법 간 loss를 품질 순위로 비교할 수 없다.
2. toy QLoRA는 수치 경로를 보기 위한 simulation이며, 실제 QLoRA는 별도의 bitsandbytes NF4 결과로 판단해야 한다.
3. offline VLM의 100%는 evaluator self-check이다.
4. 실제 VLM 결과는 단 한 이미지이므로 일반화 성능을 나타내지 않는다.
5. DPO reward accuracy가 개선되지 않아 장기 학습/평가가 필요하다.
6. Podman은 강한 실용적 경계지만 VM은 아니며 kernel/runtime 취약점은 남는다.
7. 모델이 만든 테스트도 틀릴 수 있으므로 별도 verifier와 고정 hidden test가 필요하다.

## 결론

현재 장비는 이 연구 목적에 충분하며, 특히 96GB VRAM 덕분에 3B 실제 QLoRA와 8B VLM, 30B/32B teacher 추론까지 한 머신에서 다룰 수 있다. 이번 단계에서 중요한 성과는 큰 모델을 오래 학습한 것이 아니라 다음을 같은 형식으로 재현할 기반이 생긴 것이다.

- 작은 모델에서 내부 원리를 직접 관찰
- 실제 로컬 모델에서 동일 objective가 작동하는지 검증
- simulation과 actual result를 명확히 분리
- 수치와 이미지, HTML trace를 함께 보존
- 실패도 다음 ablation에 사용할 수 있게 기록
- generated code를 일반 host process가 아닌 제한된 workspace/Podman에서 검증

다음 우선순위는 고정 validation set과 3 seed를 추가한 LoRA/QLoRA 비교, VLM 8B의 문서·차트·grounding 평가셋, 32B→8B response distillation, 코드 에이전트 constrained JSON과 hidden-test verifier다.
